# v1.3 Application ↔ Supabase Reconciliation

Date: 2026-10-04

## Finding

The engineered v1.3 source contains a Prisma/PostgreSQL repository layer, but its Prisma schema is **not equivalent to the live Supabase production schema**.

The live architecture is:

- Supabase Auth `auth.users` for identity/password/session management
- `public.profiles` for application user profile/role data
- Existing RLS policies as the production authorization boundary
- Existing public application tables for projects, bookings, payments, tickets, documents, chat, notifications, equipment, expenses, CMS, and audit logs

The v1.3 Prisma schema instead models a private `User` table containing password hashes, verification/reset tokens, login counters, and session relations.

## Do not do this

Do **not**:
- run the standalone v1.3 Prisma migrations against the production Supabase database;
- create a duplicate `users` table;
- copy password hashes into `profiles`;
- enable `DB_DRIVER=postgres` with the current Prisma schema;
- bypass Supabase RLS using a broad service-role credential in normal client requests.

## Required integration direction

The next application engineering pass should:

1. Replace custom application authentication with Supabase Auth for production login, signup, password reset, email verification, and session refresh.
2. Treat `auth.users.id` as the canonical user ID.
3. Resolve role/name/phone/address/status from `public.profiles`.
4. Preserve the existing API response shapes where practical so the client/admin portals do not require an unnecessary rewrite.
5. Map the existing route entities to the existing Supabase tables rather than introducing duplicate tables.
6. Keep service-role access server-side only for operations that genuinely require privileged execution.
7. Preserve and test the existing RLS rules for client/staff/admin separation.

## Important schema differences

The v1.3 Prisma `User` model contains fields that intentionally do not exist in production, including:

- `password`
- `emailVerificationToken`
- `emailVerificationTokenExpires`
- `resetToken`
- `resetTokenExpires`
- `failedLoginAttempts`
- `lockUntil`

Those concerns belong to Supabase Auth and should not be recreated in the application database.

Production `profiles` also does not contain an email column; email belongs to `auth.users`.

The production IDs are UUIDs generated by Postgres, while the v1.3 Prisma schema uses application-generated CUIDs.
